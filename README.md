# kmradar — радар поводов для КМ

MVP «снаружи банка»: КМ задаёт регион, отрасли (ОКВЭД), диапазон выручки и
продукты. Каждое утро получает до 7 карточек о событиях у компаний этого
профиля — только из открытых источников. Клиент это или нет, КМ проверяет сам
в банковских системах. Банковские данные в систему не попадают.

Полное описание продукта: [docs/mvp.md](docs/mvp.md).

## Быстрый старт

Python 3.10+, сторонних зависимостей нет (pytest — только для тестов).

```bash
python -m kmradar demo        # 4 дня на вымышленных компаниях Тверской области
python -m pytest -q           # тесты
```

Боевой цикл:

```bash
python -m kmradar add-km kms.json                         # профили КМ
python -m kmradar run --source data/ --out out/            # ночной прогон за сегодня
python -m kmradar run --source data/ --telegram            # то же, доставка в Telegram (TELEGRAM_TOKEN)
python -m kmradar bot                                      # приём нажатий кнопок
python -m kmradar feedback 12 contacted                    # ответ вручную (useful|miss|knew|contacted)
python -m kmradar outcome 12 meeting                       # итог (meeting|application|refusal|nothing)
python -m kmradar metrics                                  # метрики пилота с порогами
```

`run` по cron в ~03:00, дайджест уходит сразу после прогона; рассылка к 08:30 —
отдельной задачей по cron, если нужен точный час.

## Как устроено

```
источник → снимок → разница со вчера → события → скоринг → лимиты → карточка → КМ
                                                     ↑                          │
                                                     └──── обратная связь ──────┘
```

| Модуль | Что делает |
| --- | --- |
| `sources.py` | Протокол источника и `FixtureSource` (JSON по дням) |
| `diff.py` | Снимок сегодня − снимок вчера = события 2–8; протоколы ЕИС → событие 1 |
| `scoring.py` | `score = W × F × S × P × личный вес КМ` |
| `digest.py` | Склейка событий компании, стоп-сигналы, неделя тишины, лимиты 7 + 3 срочных, пропуск слабых дней |
| `cards.py` | Карточка: факты — шаблоном из данных, пустых полей нет |
| `writer.py` | «Зачем звонить / Первая фраза / Спросить»: шаблоны или LLM с проверкой |
| `feedback.py` | Кнопки, личные веса, вопрос после 3 «мимо», вопрос об итоге через 7 дней |
| `metrics.py` | Метрики пилота и пороги «идём дальше / стоп» |
| `delivery.py`, `bot.py` | Консоль, файлы Markdown (почта / веб), Telegram |
| `storage.py` | SQLite; схема переносится в Postgres |

Все веса, окна и лимиты — в `config.py`.

### Правила, которые зашиты в код

- **LLM не пишет фактов.** Цифры, даты, номера, суммы подставляются шаблоном.
  Ответ LLM отклоняется и заменяется шаблоном, если в нём есть цифры, гипотеза
  не помечена как гипотеза («скорее всего», «может») или в первом предложении
  фразы назван продукт.
- **Стоп-сигнал** (ликвидация, банкротство, крупные долги ФССП) подавляет
  карточки по компании на 90 дней и приходит строкой «⚠️ Осторожно».
- **Одна компания — одна карточка в неделю;** все свежие события компании
  склеиваются в одну карточку, срочное идёт первым. Событие, уже показанное КМ, повторно не приходит.
- **Нажимать кнопки карточки может только КМ, которому она отправлена.**

### Решения там, где документ допускает толкования

- `S` для закупок: сумма к медиане территории, потолок 2,0 **и пол 0,5** —
  иначе контракт сильно ниже медианы обнулял бы самый сильный тип сигнала.
- Пропуск дайджеста (меньше 3 сильных карточек два дня подряд) **не трогает
  срочные**: победа в закупке с окном в несколько дней уходит всё равно.
  Первый день, за который нет вчерашних данных, не считается слабым.
- «Уже знал» и «мимо» считаются от карточек с ответом, «связался» — от всех.
- Открытие дайджеста = в этот день КМ нажал хотя бы одну кнопку
  (Telegram не сообщает о прочтении).
- Окно сигнала МСП — 60 дней, отчётности — 90 (в документе «раз в год»).

## Формат данных источника

Каталог с файлами `YYYY-MM-DD.json`:

```json
{
  "snapshots": [ { "inn": "...", "name": "...", "region": "69", "okved_main": "42.11", "...": "..." } ],
  "tenders":   [ { "inn": "...", "date": "2026-10-14", "amount": 186000000, "subject": "...",
                   "customer": "...", "number": "...", "law": "44", "url": "..." } ],
  "events":    [ { "inn": "...", "type": "tender_win", "date": "2026-10-14", "facts": {}, "url": "..." } ]
}
```

Полный формат снимка — в docstring `kmradar/diff.py`, пример — `fixtures/demo/days/`.

`events` — для фазы Wizard of Oz: аналитик кладёт найденные руками события,
радар делает из них карточки по тем же правилам и считает метрики. Компания
события должна быть в `snapshots` того же или более раннего дня.

## Что дальше

1. Адаптер Checko (или Контур.Фокус) → снимки ЕГРЮЛ / МСП / Федресурс / ФССП / ГИР БО.
2. Адаптер ЕИС: индивидуальный токен или коммерческий API закупок.
3. LLM: передать в `LLMWriter` функцию вызова GigaChat API.
4. Настройка профиля КМ диалогом в боте (сейчас — `kms.json`).
5. Postgres вместо SQLite.

Открытые вопросы до пилота (ИБ и комплаенс, состав КМ, порог суммы контракта,
доступность свежей отчётности ГИР БО) — в конце [docs/mvp.md](docs/mvp.md).
